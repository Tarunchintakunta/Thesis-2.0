\chapter{Conclusions and Discussion}
\label{ch:conclusions}

This chapter summarizes the research findings, discusses their implications for serverless practitioners, acknowledges limitations, and outlines directions for future work.

\section{Summary of Contributions}

This research investigated cold-start latency reduction in AWS Lambda through developer-adjustable controls: runtime selection, package optimization, memory allocation, and low-frequency warming. The study makes four primary contributions:

\subsection{Methodological Extension}

This work extends \citet{bluemke2025ijet}'s Lambda configuration analysis framework by isolating \textit{Init Duration} from total Duration. This separation enables precise identification of initialization overhead (micro-VM creation, runtime bootstrap, dependency loading) versus handler execution time. Prior studies measuring aggregate Duration conflate these distinct phases, limiting actionable insights.

The pre-registered analysis plan (\texttt{docs/ANALYSIS\_PLAN.md}) specifies hypothesis tests, normality checks, multiple comparison correction (Holm-Bonferroni), and mandatory effect size reporting before any data collection. This approach prevents p-hacking and selective reporting, common threats to validity in performance studies \citep{wen2025variance}.

\subsection{Multi-Runtime Comparison}

This study provides the first systematic comparison of cold-start initialization across three production runtimes (Python 3.12, Node.js 20, Java 21) under controlled package-size conditions. Prior work either focuses on single runtimes \citep{bluemke2025ijet} or measures aggregate latency without isolating Init Duration \citep{wen2023characterizing}.

Proxy benchmarks (local process initialization measurements) on the GitHub Actions CI runner demonstrate:

\begin{itemize}
    \item \textbf{Package-size dominance:} Python default (21 MB) median init proxy 2383.7 ms vs. optimised (604 B) 20.9 ms—a 2362.8 ms reduction (114× speedup, rank-biserial = 1.00, p = 4.3e-14). Node.js: 293.2 ms reduction (11× speedup). Java: 185.9 ms reduction (6× speedup).
    
    \item \textbf{Runtime baseline similarity:} Optimised packages (minimal dependencies) show similar init proxy times across runtimes: Python 20.9 ms, Node.js 30.4 ms, Java 37.2 ms—within 16 ms range despite language differences (Kruskal-Wallis p = 3.4e-22, epsilon-squared = 0.85).
\end{itemize}

These findings suggest \textit{dependency bloat costs far exceed runtime choice} for initialization overhead. While these are proxy measurements (not Lambda Init Duration), they validate hypothesis directions before AWS execution.

\subsection{Decision Matrix Framework}

The decision matrix expresses optimizations as \textit{milliseconds saved per dollar per 1,000 invocations}, enabling practitioners to select strategies matching their latency and budget constraints. For example, package pruning (Python default → optimised) yields:

\begin{equation}
\text{ROI} = \frac{2362.8 \text{ ms}}{\Delta C_{1000}} \approx \infty \text{ ms/USD (negligible cost increase)}
\end{equation}

This "infinite ROI" (or near-infinite for storage costs) places package optimization in the \textbf{ADOPT} band: significant latency savings with negligible cost penalty.

In contrast, provisioned concurrency (not evaluated here but documented by AWS) eliminates cold starts but incurs continuous warm-container costs proportional to provisioned capacity—potentially \$10–\$50/month per function at 1 unit provisioned. The decision matrix would show high latency reduction but high cost, placing it in the "Consider for latency-critical only" band.

The complete experimental artefact is available in the project repository:

    \item Infrastructure-as-Code (AWS SAM template)
    \item Six Lambda function variants (verified digest uniformity)
    \item Data collection pipeline (invoke → collect → parse → cost → analyze)

\end{itemize}

All code, configurations, and documentation enable independent replication by other researchers or practitioners.

\section{Implications for Practice}

The findings (validated via proxy benchmarks, pending live Lambda confirmation) suggest three actionable recommendations for serverless practitioners:

\subsection{Recommendation 1: Aggressively Prune Dependencies}

Deploy only necessary dependencies. Python applications often accumulate boto3, requests, pandas, NumPy without removing unused imports. Our proxy benchmarks show Python's default configuration (21 MB with boto3/requests/sympy) costs 2.4 seconds of init proxy time versus 21 ms for stdlib-only. Even if Lambda Init Duration magnitudes differ, the \textit{relative} cost of bloat is likely proportional.

\textbf{Actionable steps:}
\begin{enumerate}
    \item Audit \texttt{import} statements and \texttt{package.json}/\texttt{pom.xml} dependencies
    \item Remove unused libraries
    \item Use AWS Lambda Layers for shared dependencies across multiple functions (reduces per-function size)
    \item For Python: ship pre-compiled bytecode (*.pyc) to skip on-demand compilation (future work)
\end{enumerate}

\subsection{Recommendation 2: Runtime Choice is Secondary}

For minimal packages, runtime init proxy times differ by only 16 ms (Python 20.9 ms, Node.js 30.4 ms, Java 37.2 ms on CI runner). This suggests that \textit{choosing the runtime developers are most productive in is more important than micro-optimizing cold-start milliseconds}, assuming dependencies are pruned.

However, JVM's first handler execution is slower (Java optimised: 84.8 ms handler vs. Python 8.5 ms, Node.js 38.2 ms) due to lack of JIT compilation. This cost appears in Duration (not Init Duration), so cold-start tail latency includes both initialization and uncompiled first-run overhead. Java is still viable for latency-critical applications if:

\begin{itemize}
    \item Functions execute long-running compute (amortizing first-run overhead)
    \item AWS SnapStart is enabled (Java 11/17 Corretto only, checkpoints post-initialization)
\end{itemize}

\subsection{Recommendation 3: Low-Frequency Warming for Moderate Traffic}

EventBridge scheduled invocations (every 5 minutes) provide a zero-baseline-cost alternative to provisioned concurrency for moderate-traffic functions (invoked less than once per 10 minutes). Warming pings incur only per-request (\$0.0000002) and minimal execution costs (handler returns immediately).

Estimated warming cost (per function, 5-minute schedule):
\begin{equation}
C_{\text{warming/month}} = \frac{30 \times 24 \times 60}{5} \times 0.0000002 + \text{execution} \approx \$0.0017/\text{month}
\end{equation}

Versus provisioned concurrency (1 unit at 512 MB):
\begin{equation}
C_{\text{provisioned/month}} \approx \$13/\text{month}
\end{equation}

The 7,600× cost difference makes low-frequency warming attractive for functions with unpredictable but moderate traffic.

\section{Limitations and Threats to Validity}

\subsection{Proxy Benchmarks Are Not Lambda Init Duration}

Local process benchmarks measure runtime start + package loading on bare metal (or VM), without AWS Lambda's micro-VM initialization, code download from S3, or Lambda runtime API handshake. Proxy results validate hypothesis \textit{directions} (bloated packages are slower, runtimes have similar baseline costs), but absolute magnitudes do not transfer to Lambda.

\textbf{Mitigation:} The experimental design explicitly labels proxy data as "local init benchmark" everywhere. Live Lambda data collection is required for conclusive claims about Init Duration.

\subsection{Workload Specificity}

Results apply to CPU-bound, dependency-light workloads (SHA-256 computation). I/O-bound functions (S3 access, database queries) may exhibit different init-cost profiles:

\begin{itemize}
    \item Network SDK initialization (boto3 S3 client, psycopg2 database driver) may dominate init time
    \item Compiled extensions (NumPy, pandas) may increase package-size effects
\end{itemize}

\textbf{Future work:} Extend study to representative workloads from \citet{copik2021sebs} benchmark suite (machine learning inference, image processing, web scraping).

\subsection{Temporal Generalizability}

AWS Lambda platform evolves. Runtime optimizations (Python 3.13 JIT, Node.js V8 updates, AWS Graviton3 ARM chips) may change baseline Init Duration magnitudes. Results reflect September 2026 platform state.

\textbf{Mitigation:} Reproducible artefact enables periodic re-execution to track platform evolution.

\subsection{Single-Region Evaluation}

Experiments target a single AWS region. Inter-region variance (data center hardware differences, network latency to CloudWatch) is not measured.

\textbf{Future work:} Multi-region replication to quantify geographic variance.

\section{Future Research Directions}

\subsection{Bytecode Pre-Compilation for Python}

AWS Lambda's \texttt{/var/task} directory (where function code is extracted) is read-only. Python compiles \texttt{.py} files to \texttt{.pyc} bytecode on first import, but cannot cache these files for subsequent cold starts. Shipping pre-compiled bytecode in deployment packages may eliminate AST parsing overhead.

\textbf{Hypothesis:} Python functions shipping only \texttt{.pyc} files (no \texttt{.py} source) exhibit lower Init Duration than equivalent functions shipping source.

\textbf{Implementation:}
\begin{verbatim}
python -m compileall -b functions/python/default/
find functions/python/default/ -name "*.py" -delete
zip -r python-bytecode.zip functions/python/default/
\end{verbatim}

This is a novel optimization not evaluated in prior work.

\subsection{GraalVM Native Images for Java}

GraalVM ahead-of-time (AOT) compilation produces native binaries with sub-millisecond startup times, eliminating JVM bootstrap overhead. AWS Lambda supports custom runtimes (via Amazon Linux 2 containers), enabling GraalVM deployment.

\textbf{Hypothesis:} GraalVM native images exhibit Init Duration comparable to Node.js/Python (50–100 ms) versus traditional JVM (200–500 ms).

\textbf{Challenge:} Native images require build-time class initialization and reflection configuration, increasing deployment complexity.

\subsection{SnapStart Evaluation for Java}

AWS SnapStart (Java 11/17 Corretto only) checkpoints initialized containers and restores snapshots on cold starts, eliminating runtime bootstrap and application initialization. Evaluation requires:

\begin{itemize}
    \item Java 11 or 17 Corretto runtime (current study uses Java 21)
    \item Account-level SnapStart enablement
    \item Modification to avoid non-deterministic initialization (e.g., random seeds, timestamps)
\end{itemize}

\textbf{Expected outcome:} SnapStart eliminates Init Duration entirely for compliant functions, at zero cost beyond standard Lambda pricing.

\subsection{Real-World Workload Evaluation}

Extend the study to production-like workloads:

\begin{itemize}
    \item Machine learning inference (TensorFlow, PyTorch)
    \item Image processing (PIL, OpenCV)
    \item Database access (psycopg2, pymysql)
    \item API aggregation (multiple external HTTP calls)
\end{itemize}

These workloads have large dependencies (hundreds of MB for ML models) and complex initialization (model loading, connection pooling), potentially amplifying package-size effects.

\subsection{Cost-Benefit Analysis of Provisioned Concurrency}

Quantify the traffic threshold where provisioned concurrency becomes cost-effective:

\begin{equation}
\text{Break-even rate} = \frac{C_{\text{provisioned}}}{C_{\text{per-cold-start}} \times p_{\text{cold}}}
\end{equation}

where $p_{\text{cold}}$ is cold-start frequency under various traffic patterns.

\section{Final Remarks}

This research demonstrates that developer-adjustable controls—particularly deployment package optimization—offer significant cold-start latency reduction with minimal cost increase. Proxy benchmark results suggest package-size effects dominate runtime selection, challenging the conventional wisdom that "choosing the fastest runtime" is the primary optimization lever.

The study's rigorous methodology (pre-registered hypotheses, explicit Init Duration isolation, data provenance tracking, reproducible artefact) establishes a template for future serverless performance investigations. The decision matrix framework enables practitioners to make evidence-based trade-offs between latency improvement and cost overhead.

While live AWS Lambda validation is required to confirm absolute Init Duration magnitudes, the proxy benchmarks provide strong directional evidence: \textit{prune dependencies first, choose runtimes second, provision continuously only as a last resort}.
