\section{Pilot Phase: Repeatability and Power}

\subsection{Repeatability}

The pilot tested 3 configurations (VT 30/300/900, batch 10, MRC 3, no fault) with 3 repeats each. Coefficient of variation (CV) for key metrics:
\begin{itemize}
    \item Throughput: CV < 0.01 (highly repeatable)
    \item Latency: CV < 0.05 (acceptable)
    \item Loss: 0.0 in all runs (no variance)
    \item Duplicates: CV ~0.2 (expected for stochastic at-least-once)
\end{itemize}

\textbf{Conclusion:} Simulator produces consistent results; seeds control randomness effectively.

\subsection{Power Analysis}

Pilot runs estimated effect sizes for recovery time (VT 30 vs. 900 under consumer kill): Cohen's d ≈ 3.5 (very large). Power analysis (Mann-Whitney U, α=0.05, power=0.80) indicated N=3 per group sufficient for detecting large effects. Campaigns used 5 repeats for conservatism.

\section{Baseline Replication: Steady-State Validation}

\subsection{Comparison with Kyrychenko et al. (2025)}

The baseline phase replicated \citet{Kyrychenko2025} steady-state conditions (no faults). Key findings:

\begin{itemize}
    \item \textbf{Batch size dominates throughput:} Median throughput ~161 msg/s at batch 1, ~375 msg/s at batch 50 (5 pollers). Matches Kyrychenko's qualitative finding ("batch size is key factor").
    
    \item \textbf{Visibility timeout does not affect steady-state throughput:} Throughput variance across VT 30-900 < 5\%. Confirms Kyrychenko's result.
    
    \item \textbf{Duplicate floor:} Median duplicate rate ~0.002 (0.2\%) from at-least-once delivery, consistent across configs. No simulation artifact.
    
    \item \textbf{Delivery delay shifts latency:} Delay 300 adds ~300s to median latency; throughput unaffected. Expected.
\end{itemize}

\textbf{Conclusion:} Simulator replicates steady-state \emph{relative effects} from Kyrychenko et al. Absolute throughput differs (simulator is faster, no network overhead), but configuration trade-offs match. Simulator is valid for testing fault scenarios.

\section{Arms Comparison: Control Validation}

The sync vs. queue arms were compared under (1) no fault and (2) consumer\_kill fault (10s).

\textbf{No Fault:}
\begin{itemize}
    \item Sync arm: 0.0\% loss, median latency ~50ms, throughput limited by sequential processing.
    \item Queue arm: 0.0\% loss, median latency ~120ms (includes queue delay), throughput ~350 msg/s (batch 50).
\end{itemize}

\textbf{Consumer Kill (10s):}
\begin{itemize}
    \item Sync arm: 0.3\% loss (client retry budget exhausted for messages sent during fault window), recovery immediate after fault stop.
    \item Queue arm: 0.0\% loss (redelivery from SQS), recovery time ~35s (VT 30).
\end{itemize}

\textbf{Interpretation:} Sync arm demonstrates that faults \emph{do} cause loss without queueing; queue arm's zero loss validates DLQ + redelivery mechanism. Control arm is valid baseline.

\section{Hypothesis Test Results}

All hypothesis tests used α = 0.05 and Holm-Bonferroni correction for family-wise error rate control.

\subsection{H1: Message Loss}

\textbf{Hypothesis:} SQS queue arm with DLQ, VT ≥ 900, MRC ≥ 3 has negligible loss (< 0.1\%) vs. sync arm under faults.

\textbf{Test:} Mann-Whitney U comparing queue arm (configs with VT ≥ 900, MRC ≥ 3, N=45 runs) vs. sync arm (N=10 runs) under each fault type.

\textbf{Result:}
\begin{itemize}
    \item Queue arm: Mean loss 0.00\%, SD 0.00\% (zero in all runs).
    \item Sync arm: Mean loss 0.18\%, SD 0.12\% (range 0.1–0.6\%).
    \item Mann-Whitney U: p < 0.001 (raw), p < 0.003 (Holm-adjusted), rank-biserial r = 1.0 (perfect separation).
\end{itemize}

\textbf{Conclusion:} \textbf{H1 supported.} SQS configuration with DLQ and sufficient VT/MRC prevents message loss under failure. Zero loss observed across all fault types (consumer kill, unhandled error, datastore reject, datastore timeout). DLQ captures messages that fail repeatedly; redelivery ensures eventual processing.

\subsection{H2: maxReceiveCount Independence for Transient Faults}

\textbf{Hypothesis:} Recovery time after transient fault (consumer\_kill, 10s) does not differ significantly across MRC ∈ \{1, 3, 5, 10\} at VT = 30.

\textbf{Test:} Kruskal-Wallis H comparing recovery time distributions for 4 MRC groups (N=5 per group).

\textbf{Result:}
\begin{itemize}
    \item MRC 1: Median recovery 33s, IQR [31, 36]
    \item MRC 3: Median recovery 34s, IQR [32, 35]
    \item MRC 5: Median recovery 36s, IQR [33, 37]
    \item MRC 10: Median recovery 35s, IQR [33, 38]
    \item Kruskal-Wallis H: p = 0.42 (raw), η² = 0.04 (very small effect).
\end{itemize}

\textbf{Conclusion:} \textbf{H2 supported.} Recovery time for transient faults is independent of MRC; differences are negligible (2–3 seconds, well within noise). However, \textbf{DLQ traffic differs substantially}:
\begin{itemize}
    \item MRC 1: 29\% of messages moved to DLQ (unnecessarily dead-lettered; would succeed on retry).
    \item MRC 3: 2\% to DLQ.
    \item MRC 5: 0.5\% to DLQ.
    \item MRC 10: 0.1\% to DLQ.
\end{itemize}

\textbf{Practical Implication:} For transient faults, set MRC ≥ 3 to avoid unnecessary DLQ traffic. Higher MRC (≥5) introduces minimal additional benefit for transient faults but increases duplicate rate slightly (more retries → more redeliveries).

\subsection{H3: Steady-State Optimum Transfer}

\textbf{Hypothesis:} Steady-state-optimal config (batch 50, VT 600) has significantly longer recovery time than alternatives (batch 10/1, VT 30) under consumer\_kill.

\textbf{Test:} Mann-Whitney U comparing (batch 50, VT 600) vs. pooled alternatives (batch 10 VT 30, batch 1 VT 30, batch 50 VT 30).

\textbf{Result:}
\begin{itemize}
    \item (Batch 50, VT 600): Median recovery ~600s, IQR [595, 605]
    \item Alternatives: Median recovery ~36s, IQR [32, 40]
    \item Mann-Whitney U: p = 0.021 (raw), p = 0.084 (Holm-adjusted), rank-biserial r = 0.67 (large effect).
\end{itemize}

\textbf{Conclusion:} \textbf{H3 partially supported.} Recovery time for steady-state-optimal config is ~16× longer (600s vs. 36s), with large effect size (r = 0.67). However, after Holm-Bonferroni correction, p = 0.084 > 0.05, so the result is not statistically significant at the family-wise level. 

\textbf{Interpretation:} The evidence \emph{suggests} that long VT delays recovery, but the hypothesis test was under-powered due to pooling heterogeneous alternatives (which increased variance). Post-hoc pairwise comparison (batch 50 VT 600 vs. batch 50 VT 30 only) yields p < 0.01 (significant). 

\textbf{Practical Implication:} Visibility timeout is the dominant factor in recovery time. Long VT (600s) optimizes steady-state latency but delays redelivery after failure. Practitioners should \textbf{balance latency optimization vs. recovery responsiveness}: use shorter VT (30–120s) for workloads where fast recovery is critical, even if it slightly increases steady-state latency (due to premature visibility timeout expiry during long-running processing).

\section{Key Findings}

\subsection{Recovery Time Follows Visibility Timeout 1:1}

Figure \texttt{recovery\_vs\_visibility.png} shows recovery time increases linearly with VT (slope ≈ 1.0, R² = 0.98). Example:
\begin{itemize}
    \item VT 30: ~35s recovery
    \item VT 120: ~122s recovery
    \item VT 600: ~600s recovery
\end{itemize}

\textbf{Mechanism:} Messages sent during fault window are received, fail, enter in-flight state with VT timer. They become visible again only after VT expires. Consumer then reprocesses them. Total recovery ≈ VT + processing time.

\textbf{Implication:} \textbf{VT is a recovery time knob.} Set it based on acceptable recovery SLA, not just steady-state processing time.

\subsection{DLQ Traffic Depends on maxReceiveCount and Fault Type}

Figure \texttt{dlq\_vs\_max\_receive\_count.png} (heatmap by fault type):

\textbf{Transient faults (consumer\_kill, datastore\_timeout):}
\begin{itemize}
    \item MRC 1: 25–30\% to DLQ (too aggressive)
    \item MRC 3: 1–3\% to DLQ (acceptable)
    \item MRC ≥ 5: < 1\% to DLQ
\end{itemize}

\textbf{Deterministic-like faults (unhandled\_error, datastore\_reject):}
\begin{itemize}
    \item MRC 1: 15–20\% to DLQ (some messages would succeed on retry due to transient conditions)
    \item MRC 3: 8–12\% to DLQ
    \item MRC ≥ 5: 5–8\% to DLQ (diminishing returns; truly broken messages eventually DLQ'd)
\end{itemize}

\textbf{Implication:} \textbf{Tune MRC to failure pattern.} If failures are mostly transient (downstream recovers quickly), MRC 2–3 minimizes DLQ noise. If deterministic poison messages are common, MRC 1–2 quarantines them faster, freeing resources.

\subsection{Duplicates Over Baseline Floor}

Figure \texttt{duplicates\_over\_floor.png}: Baseline duplicate rate ~0.002 (from at-least-once delivery). Under failure:
\begin{itemize}
    \item MRC 1: +0.001 (negligible increase; most messages DLQ'd before duplicate)
    \item MRC 3: +0.01 (1\% additional duplicates from retries)
    \item MRC ≥ 5: +0.14 (14\% additional duplicates; more retries → more redeliveries)
\end{itemize}

\textbf{Implication:} Higher MRC trades DLQ traffic for duplicate processing. With idempotent consumers, this is acceptable. Without idempotency, high MRC risks duplicate side effects.

\subsection{Batch Size and Recovery}

Batch size has minimal effect on recovery time (p = 0.31, η² = 0.03). Recovery is dominated by VT. However, larger batches amplify \emph{in-flight backlog} during failure (more messages in single failed batch), slightly increasing visible depth spike. Effect is small (< 10\% difference).

\section{Summary}

The evaluation confirms:
\begin{itemize}
    \item \textbf{SQS DLQ + redelivery prevents message loss} (H1 supported).
    \item \textbf{Recovery time is independent of MRC for transient faults} (H2 supported), but DLQ traffic differs.
    \item \textbf{Long VT delays recovery} (H3 large effect, borderline significance after correction).
    \item \textbf{Visibility timeout is the primary recovery time determinant} (1:1 relationship).
    \item \textbf{MRC should match failure pattern} (2–3 for transient, 1–2 for deterministic).
    \item \textbf{Batch size has minimal recovery impact}; optimize for throughput.
\end{itemize}

Findings provide empirical, statistically rigorous guidance for SQS configuration under failure scenarios, extending \citet{Kyrychenko2025} steady-state baseline to real-world resilience requirements.
