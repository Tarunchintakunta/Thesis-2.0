\begin{abstract}

Cloud-native applications increasingly rely on asynchronous message queues for decoupling, scalability, and fault isolation. Amazon Simple Queue Service (SQS) is a widely adopted managed queueing service that provides at-least-once delivery guarantees and integrates seamlessly with AWS Lambda. While prior research has optimized SQS configuration for steady-state performance~\citep{Kyrychenko2025}, the behavior of visibility timeout, \texttt{maxReceiveCount}, and batch size parameters under consumer and downstream failures remains unquantified.

This research investigates the research question: \textbf{How does Amazon SQS configuration affect message reliability and recovery under injected consumer and downstream failures?} A controlled experimental artefact was developed using AWS Serverless Application Model (SAM), implementing a two-arm comparison (synchronous API vs. SQS queue) with an in-process fault injection switch capable of triggering consumer kills, unhandled errors, datastore rejections, and datastore timeouts at deterministic times. A discrete-event simulator enables reproducible experiments without AWS account costs.

The study measures message loss, duplicate processing, dead-letter queue (DLQ) traffic, recovery time, throughput, and latency across 350+ experimental runs spanning visibility timeout (30–900 seconds), \texttt{maxReceiveCount} (1–10), batch size (1–50), and four fault types. Three pre-registered hypotheses are tested with Holm-Bonferroni correction: (H1) SQS configuration prevents message loss under failure; (H2) transient faults' recovery time is independent of \texttt{maxReceiveCount}; (H3) steady-state-optimal configurations have longer recovery time than alternatives.

Key findings include: (1) Zero message loss observed in the queue arm across all configurations, validating DLQ and redelivery mechanisms. (2) Recovery time follows visibility timeout nearly 1:1 (e.g., 600-second timeout yields ~600-second recovery), with large effect size (rank-biserial r = 0.67). (3) \texttt{maxReceiveCount} does not significantly affect recovery duration for transient faults but determines DLQ traffic: low values (1–2) unnecessarily dead-letter recoverable messages; high values (≥5) introduce duplicate processing. (4) The configuration optimized for steady-state throughput (batch 50, visibility timeout 600) exhibits substantially longer recovery time (~600 seconds) than shorter-timeout alternatives (~36 seconds at visibility timeout 30), though statistical significance does not survive Holm correction (adjusted p = 0.084).

The research contributes empirical, statistically validated evidence on SQS resilience configuration, a reproducible fault injection framework, and quantitative guidance for practitioners. Results indicate that visibility timeout is the dominant factor in recovery time, suggesting practitioners should balance steady-state latency optimization against failure recovery responsiveness. \texttt{maxReceiveCount} should be set based on observed failure patterns: 2–3 for transient-only failures; 5–10 when deterministic poison messages are rare and downstream outages may last minutes.

Future work includes live AWS validation to quantify simulator fidelity, extension to FIFO queues and multi-region architectures, and comparison with alternative brokers (Kafka, RabbitMQ). The complete artefact (SAM template, simulator, tests, 350+ run manifests, 11 figures, statistical analysis) is provided in the repository for reproducibility and extension.

\end{abstract}
