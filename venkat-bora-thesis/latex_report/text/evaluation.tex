\chapter{Evaluation}

This chapter presents experimental results, analyzes performance trends, and interprets findings in the context of the research question: how do multi-threaded and distributed parallelism models compare for matrix workloads at matched core counts?

\textbf{Evidence boundary:} All numbers below are taken from committed \texttt{results/data/summary\_statistics.json} (local Dask \texttt{LocalCluster} on one host). No AWS EC2 multi-instance campaign was executed; these results are a local proxy, not matched-vCPU cloud results.

\section{Dataset Overview}

The benchmark suite executed successfully, generating:

\begin{itemize}
    \item \textbf{Total configurations tested}: 90 unique (parallelism model, matrix size, worker count) combinations
    \item \textbf{Total runs}: 270 (90 configurations × 3 iterations; \texttt{n\_iterations: 3} in JSON)
    \item \textbf{Matrix sizes}: 200×200, 500×500, 1000×1000, 1500×1500, 2000×2000
    \item \textbf{Worker counts}: 1, 2, 4, 8 (distributed requires ≥2 workers)
    \item \textbf{Operations}: Matrix multiplication and LU factorization
\end{itemize}

All raw data is available in \texttt{results/data/} for verification and further analysis.

\section{Completion Time Analysis}

\subsection{Matrix Multiplication Performance}

Figure~\ref{fig:completion_time} shows completion time versus matrix size for different parallelism models at 4 workers.

\begin{figure}[ht]
\centering
\includegraphics[width=0.95\textwidth]{figures/completion_time_comparison.png}
\caption{Completion time comparison for matrix multiplication (left) and worker scaling analysis (right). Multi-threaded execution maintains advantage for small to medium matrices, while distributed overhead dominates at small scales.}
\label{fig:completion_time}
\end{figure}

\textbf{Key Observations} (matmul means from JSON):

\begin{enumerate}
    \item \textbf{Small Matrices (200×200, 4 workers)}: Threading $\approx$1.09\,ms; multiprocessing $\approx$32.9\,ms; distributed $\approx$181\,ms. Local-Dask distributed is about two orders of magnitude slower than threading at this size (cluster setup and serialization dominate).
    
    \item \textbf{Medium Matrices (1000×1000)}: Threading $\approx$67.2\,ms (1 worker) / $\approx$62.2\,ms (4 workers); multiprocess $\approx$208--453\,ms; local-Dask distributed $\approx$206--345\,ms (2--4 workers). Distributed remains slower than threading at matched worker counts.
    
    \item \textbf{Worker Scaling (1000×1000 vs 1-worker threaded baseline)}: Doubling workers from 1 to 2 improves threading by $\approx$1.32× (sub-linear). At 4 workers, threaded speedup is only $\approx$1.08× (not $\sim$2.1×). Distributed speedups vs the same baseline are below 1.0 (0.33× at 2 workers, 0.20× at 4 workers).
\end{enumerate}

\subsection{LU Factorization Performance}

Figure~\ref{fig:lu_comparison} compares LU factorization performance.

\begin{figure}[ht]
\centering
\includegraphics[width=0.8\textwidth]{figures/lu_factorization_comparison.png}
\caption{LU factorization completion time across matrix sizes. The sequential nature of Gaussian elimination limits parallel efficiency.}
\label{fig:lu_comparison}

LU factorization shows less parallel speedup than matrix multiplication due to its inherently sequential column-elimination structure. At 1000×1000, threaded LU speedup vs 1-worker threaded LU is $\approx$1.60× at 2 workers and $\approx$1.40× at 4 workers (JSON). Distributed LU remains slower than threaded LU at matched worker counts in the committed suite.

\textbf{Memory Observations} (1000×1000 matmul, JSON \texttt{mean\_memory}):

\begin{enumerate}
    \item \textbf{Threading}: $\approx$227\,MB (1 worker) / $\approx$347\,MB (4 workers)
    \item \textbf{Multiprocessing}: $\approx$289\,MB (1 worker) / $\approx$417\,MB (4 workers)
    \item \textbf{Distributed}: $\approx$340\,MB (2 workers) / $\approx$395\,MB (4 workers)
\end{enumerate}

Memory overhead grows with matrix size. For 1000×1000 double-precision matrices, theoretical minimum for three matrices is $3\times8\times10^6 = 24$\,MB. Observed RSS includes Python runtime, NumPy structures, and framework bookkeeping.

\section{Crossover Analysis}

\subsection{Does a Crossover Exist?}

Within the full committed local suite (200--2000, workers 1--8), \textbf{no crossover} was observed for matmul: distributed mean time never beats threaded mean time at the same worker count. At 2000×2000 with 4 workers, threading is still faster ($\approx$651\,ms vs $\approx$1099\,ms; ratio $\approx$1.69×).

At 1000×1000 with 4 workers (often cited as the mid-range point):
\begin{itemize}
    \item Threading: $\approx$62.2\,ms
    \item Distributed: $\approx$344.6\,ms
    \item Ratio: distributed $\approx$5.54× slower (not a 47\% gap)
\end{itemize}

The absolute gap narrows at some larger sizes relative to tiny matrices, but \textbf{distributed still does not win through 2000×2000} in the local JSON. Any claim that crossover ``typically'' occurs near 1000×1000 is withdrawn for this evidence set. A true multi-node EC2 campaign (CA2 matched aggregate vCPUs) was not run; network latency would likely increase distributed cost further.

\subsection{Hypothesis Testing Results}

Committed analysis reports descriptive statistics (mean $\pm$ std over $n{=}3$ iterations). Inferential procedures (Shapiro--Wilk, $t$-tests / Mann--Whitney, Holm--Bonferroni) are described in the methodology chapter but \textbf{are not implemented} as artefacts under \texttt{distributed-matrix-scaling/}; no $p$-values are claimed here.

\textbf{Hypothesis 1 (Crossover Existence)}: \textit{Not supported} within the tested local range. Distributed does not outperform threading at any (size, worker) matmul combination in JSON.

\textbf{Hypothesis 2 (Utilization Inefficiency)}: \textit{Directionally supported} by descriptive CPU means (distributed lower than threading at matched mid-range configs).

\textbf{Hypothesis 3 (Memory Limiting Factor)}: \textit{Partially supported} descriptively. Distributed RSS is higher than threading at several points, but absolute values remain modest relative to modern instance memory; coordination overhead dominates the time difference.

\section{Comparison with Baseline Literature}

\subsection{Sabir \& Alebrahim (2025) Replication}

Our threading results align directionally with their sub-linear shared-memory findings:
\begin{itemize}
    \item Sub-linear speedup (1.08× for 4 workers vs ideal 4× on this local suite)
    \item Efficiency decreases with worker count
    \item LU factorization parallelizes less effectively than matrix multiplication
\end{itemize}

\subsection{Distributed Literature}

Our local-Dask overhead pattern is consistent with the general finding that coordination can dominate at modest problem sizes. Kim et al. (2022) report higher multi-worker speedups on different workloads/hardware; our local efficiency at 4 workers ($\approx$5\% for distributed matmul speedup/workers) is lower, reflecting this workload and single-host LocalCluster overhead rather than a replicated multi-node campaign.

\section{Practical Implications}

\subsection{Decision Framework}

For matrix workloads \textit{on evidence from this local proxy}:

\begin{enumerate}
    \item \textbf{Matrix Size}: Through 2000×2000 in the committed suite, threading remains faster than local distributed at matched worker counts.
    
    \item \textbf{Single-Machine Capacity}: If the workload fits on one machine's cores, threading is more efficient in these data. Distribute only when exceeding single-node capacity—and validate on real multi-node infrastructure.
    
    \item \textbf{Memory Constraints}: If per-node memory is limited, distributing across machines can provide aggregate memory even if slower per-operation.
    
    \item \textbf{Cost Model}: Threading minimizes coordination overhead and instance count. True cloud scale-out economics require an EC2 campaign that was not executed here.
\end{enumerate}

\subsection{Cloud Infrastructure Recommendations}

Recommendations below are \textbf{methodological guidance}, not measured EC2 results:

\begin{itemize}
    \item For batch matrix jobs that fit on one host: prefer a single large instance and shared-memory parallelism first
    \item For jobs exceeding single-node capacity: run a matched-vCPU multi-instance EC2 campaign before assuming crossover
    \item For sustained workloads: amortize cluster setup overhead across multiple operations
    \item Local Dask \texttt{LocalCluster} understates multi-node network cost relative to AWS
\end{itemize}

\section{Limitations}

\subsection{Experimental Scope}

\begin{itemize}
    \item Full local sweep covers 200--2000; still no AWS multi-node campaign
    \item Local execution understates true network latency; AWS EC2 would add distributed overhead not present here
    \item Dense matrices only; sparse workloads have different communication patterns
    \item Inferential statistical tests described but not coded; $n{=}3$ iterations (not 5)
\end{itemize}

\subsection{Generalizability}

\begin{itemize}
    \item Results are CPU platform-specific (x86-64, OpenBLAS)
    \item Python-specific runtime characteristics (GIL, NumPy kernel behavior)
    \item Dask-specific coordination overhead; other frameworks (Spark, Ray) may differ
    \item Local matched cores $\neq$ CA2 matched aggregate vCPUs across EC2 instances
\end{itemize}

\section{Summary}

Experimental results from committed local JSON demonstrate that multi-threaded execution maintains performance advantages over local-Dask distributed execution for matrix workloads from 200×200 through 2000×2000 at matched worker counts. At 1000×1000 / 4 workers, distributed matmul is $\approx$5.54× slower than threading (62.2\,ms vs 344.6\,ms). No crossover appears in the local evidence set.

These findings support preferring scale-up (threading) for workloads that fit on a single host in this local proxy. They do \textbf{not} constitute measured AWS EC2 matched-vCPU results required by the CA2 cloud-instance research design.
