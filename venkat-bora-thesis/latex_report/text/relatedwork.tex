\chapter{Related Work}

This chapter critically reviews existing literature on parallel matrix operations, identifying how multi-threaded and distributed approaches have been studied separately but never systematically compared at matched resource levels. The review is organized by the key dimensions relevant to this research: shared-memory parallelism limits, distributed computing scalability, cloud infrastructure considerations, and the specific gap this work addresses.

\section{Shared-Memory Parallelism and Its Limits}

\subsection{The Sabir and Alebrahim Baseline}

Sabir and Alebrahim (2025) \cite{sabir2025coarse} provide the methodological foundation for this work. Their study implements coarse-grained column agglomeration for LU factorization without pivoting in MATLAB R2020b, testing on matrices from 100×100 to 15,000×15,000 using 2-4 threads on a four-core Xeon E3-1220 v3 processor. 

Key findings include:
\begin{itemize}
    \item Parallel speedup is consistently sub-linear—doubling cores does not double performance
    \item Communication and synchronization overhead increases with thread count
    \item MATLAB's SPMD (Single Program Multiple Data) model introduces coordination costs
    \item No exploration of distributed (scale-out) alternatives
\end{itemize}

Their explicit identification of the missing scale-out comparison motivates the present study. We adopt their LU factorization workload and extend it with distributed implementations at matched core counts.

\subsection{Runtime and Language Constraints}

Ruys et al. (2025) \cite{ruys2025performance} examine how Python runtimes constrain parallel performance, particularly the Global Interpreter Lock (GIL) serialization of pure-Python threads. Their work demonstrates that:

\begin{itemize}
    \item Native numerical kernels (NumPy, SciPy) release the GIL during computation
    \item Pure-Python threading remains serialized, limiting applicability
    \item Multi-device task parallelism varies significantly across Python implementations
\end{itemize}

This finding informed our decision to control NumPy threading explicitly and measure library-level parallelism rather than application-level thread counts. Without this control, performance differences could reflect runtime artifacts rather than the parallelism model under test.

\subsection{Diagnosing Parallel Inefficiency}

Jin et al. (2025) \cite{jin2025leveraging} develop graph-based analysis techniques to identify root causes of scaling loss in parallel applications. They attribute common performance ceilings to:

\begin{enumerate}
    \item Load imbalance across workers
    \item Resource contention (memory bandwidth, cache)
    \item Inter-process communication bottlenecks
\end{enumerate}

Critically, their work shows that scaling limits are not fixed hardware ceilings but emergent properties of workload distribution and runtime coordination. This supports the hypothesis that a different parallelism model (distributed rather than threaded) might exhibit different scaling characteristics on the same hardware.

\section{Distributed Computing Scalability}

\subsection{Cloud-Based Distributed Matrix Operations}

Kim, Son, and Lee (2022) \cite{kim2022mpec} model distributed matrix multiplication performance on cloud instances, finding that workers return results 2.5× faster than baseline—sub-linear but substantial. Their MPEC (Matrix Product on Elastic Cloud) model captures:

\begin{itemize}
    \item Network communication latency
    \item Data partitioning overhead
    \item Worker synchronization costs
\end{itemize}

However, their study does not provide a single-node multi-threaded baseline on equivalent hardware, making direct comparison impossible. The speedup is reported relative to sequential execution, not to an alternative parallelism model at the same total core count.

\subsection{The Distributed Scaling Knee}

Buyukkaya et al. (2024) \cite{buyukkaya2024stochastic} identify a performance ``knee'' in distributed stochastic gradient descent, occurring around 32 machines for their workload. Importantly, they note this knee is not a fixed threshold—it moves with dataset size and algorithmic characteristics.

This observation has two implications for the present study:
\begin{enumerate}
    \item A crossover point, if it exists, is workload-dependent and must be measured empirically rather than assumed
    \item Reporting results across multiple matrix sizes is essential to characterize where the curve shifts
\end{enumerate}

\subsection{Cloud Penalty and Configuration Effects}

Dancheva, Alonso, and Barton (2024) \cite{dancheva2024cloud} measure cloud infrastructure overhead for HPC applications on Amazon EC2. Their key finding: with appropriate tuning (instance selection, network configuration, MPI settings), cloud deployments can preserve 90\%+ of the relative speedup achievable on dedicated supercomputers.

This result challenges the assumption of an inherent ``cloud penalty.'' Performance differences often attributed to cloud infrastructure are actually configuration artifacts. For this study, it means that local measurements, while not capturing true multi-node network latency, remain methodologically sound for comparing parallelism models, with the understanding that AWS deployment would amplify the distributed overhead component.

\section{Framework and Implementation Comparisons}

\subsection{Dask vs. Spark Performance}

Dugre, Hayot-Sasson, and Glatard (2023) \cite{dugre2023performance} compare Dask and Apache Spark on HPC systems for neuroimaging workloads. Crucially, they find that:

\begin{itemize}
    \item Framework choice impacts performance by 1.79×-2.71×
    \item Memory provisioning per worker can create apparent performance differences
    \item Fair comparison requires instrumenting peak memory in addition to completion time
\end{itemize}

This motivated our inclusion of memory measurement alongside time and CPU metrics. Without it, observed ``performance differences'' might actually reflect provisioning decisions rather than algorithmic efficiency.

\subsection{Task Granularity Effects}

Kerney et al. (2024) \cite{kerney2024towards} demonstrate that task granularity, not framework identity, primarily dictates parallel efficiency in Python libraries. Fine-grained tasks incur higher coordination overhead; coarse-grained tasks amortize that cost.

For this study, the implication is that matrix size becomes a proxy for task granularity. Small matrices (200×200) represent fine-grained workloads where coordination dominates; large matrices (2000×2000) represent coarse-grained workloads where computation amortizes overhead. The crossover point, if it exists, should appear as matrix size increases.

\section{Cross-Platform and Accelerator Considerations}

Torres Niño et al. (2025) \cite{torres2025cross} evaluate matrix multiplication across MKL, cuBLAS, and SYCL backends, finding substantial performance variation (2-3×) depending on platform and optimization. Their work underscores that algorithmic complexity alone does not determine runtime; library implementation and hardware characteristics matter.

For reproducibility, this study pins Python versions, NumPy builds, and numerical kernel configurations. Results are specific to the CPU platform tested but the methodology generalizes.

\section{Research Expectations}

Based on the literature, three hypotheses guide the experimental design:

\begin{enumerate}
    \item \textbf{Crossover Existence}: A crossover point exists within the tested range, where distributed execution becomes faster than multi-threaded execution. Counter-hypothesis: one model dominates at all scales (Thomas \& Kumar, 2018 \cite{thomas2018comparative} provide evidence that this is possible).
    
    \item \textbf{Utilization Inefficiency}: Distributed models exhibit lower per-core utilization below the crossover point, indicating billed but unused capacity (based on Luan et al., 2023 \cite{luan2023exoshuffle} shuffle overhead findings).
    
    \item \textbf{Memory as Limiting Factor}: At small matrix sizes, per-worker memory provisioning rather than computation time may drive the performance difference (based on Dugre et al., 2023 \cite{dugre2023performance}).
\end{enumerate}

These expectations are tested empirically in Chapter 6.

\section{Summary}

The literature establishes that both multi-threaded and distributed parallelism exhibit sub-linear scaling, but the relative performance at matched resource levels remains unmeasured. This work fills that gap by controlling for total core count and systematically varying only the parallelism model, providing the first direct comparison for matrix workloads on cloud-scale infrastructure.
