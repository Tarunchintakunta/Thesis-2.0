\chapter{Conclusion}

\section{Summary of Contributions}

This project systematically compared multi-threaded and distributed parallelism models for dense matrix operations, addressing a gap in the literature where these approaches had been studied separately but never at matched resource levels. The work extends Sabir and Alebrahim's (2025) multi-threaded LU factorization baseline by adding comprehensive distributed comparisons under controlled experimental conditions.

Key contributions include:

\begin{enumerate}
    \item \textbf{Empirical Comparison}: Direct measurement of threading, multiprocessing, and distributed (Dask) models on identical workloads with matched total core counts, isolating the parallelism model as the independent variable.
    
    \item \textbf{Comprehensive Metrics}: Collection of completion time, peak memory consumption, and CPU utilization efficiency—addressing the literature gap where studies often report only time or omit memory.
    
    \item \textbf{Descriptive reporting}: Three iterations per configuration in committed JSON (mean$\pm$std). Inferential significance testing with Holm-Bonferroni was planned in methodology but is \textbf{not} implemented in the artefact tree.
    
    \item \textbf{Production-Quality Tooling}: A tested benchmarking framework (\textbf{20} pytest functions in tree) with automated metric collection, result storage, and visualization generation.
    
    \item \textbf{Reproducibility}: Complete source code, test suites, and documentation enabling independent verification and extension to other workloads or cloud platforms.
\end{enumerate}

\section{Key Findings}

\subsection{Performance Comparison}

Within the committed local suite (200--2000 matrix dimensions, workers 1--8; \texttt{n\_iterations: 3}):

\begin{itemize}
    \item \textbf{Threading dominates}: At 1000×1000 / 4 workers matmul, threading $\approx$62.2\,ms vs distributed $\approx$344.6\,ms ($\approx$5.54× slower for local Dask)
    \item \textbf{Overhead remains large}: At 200×200 / 4 workers, distributed $\approx$181\,ms vs threading $\approx$1.09\,ms; at 2000×2000 / 4 workers, distributed is still $\approx$1.69× slower
    \item \textbf{No crossover observed}: Distributed did not outperform threading at any (size, worker) matmul combination in JSON
\end{itemize}

\subsection{Efficiency Analysis}

\begin{itemize}
    \item \textbf{Sub-linear scaling}: Threading speedups vs 1-worker threaded baseline at 1000×1000: 1.32× (2 workers), 1.08× (4), 1.02× (8)
    \item \textbf{Threading efficiency}: $\approx$66\% at 2 workers, $\approx$27\% at 4 workers (speedup/workers)
    \item \textbf{Distributed efficiency}: $\approx$16\% at 2 workers, $\approx$5\% at 4 workers (speedups below 1.0 vs threaded baseline)
    \item \textbf{CPU utilization (1000×1000 matmul JSON)}: Threading $\approx$80--84\%; distributed $\approx$43--53\% at 2--4 workers
\end{itemize}

\subsection{Memory Overhead}

\begin{itemize}
    \item At 1000×1000 / 4 workers matmul: threading $\approx$347\,MB; distributed $\approx$395\,MB (JSON)
    \item Absolute values remain modest relative to modern instance RAM; coordination overhead, not memory, drives the time difference
\end{itemize}

\section{Practical Recommendations}

For practitioners deploying matrix workloads on cloud infrastructure:

\subsection{Scale-Up (Threading) When:}

\begin{itemize}
    \item Workload fits on a single large instance's cores and memory
    \item Matrix dimensions within the local suite through 2000×2000 (JSON: threading still faster)
    \item Minimizing coordination overhead is critical
    \item Cost sensitivity requires minimizing instance count
\end{itemize}

\subsection{Scale-Out (Distributed) When:}

\begin{itemize}
    \item Workload exceeds single-node capacity (cores or memory)
    \item Matrix dimensions beyond the local evidence set, \textbf{after} completed multi-instance EC2 matmul confirms crossover
    \item Need for fault tolerance and job elasticity outweighs overhead
    \item Running sustained workloads that amortize cluster setup cost
\end{itemize}

\subsection{Cloud Instance Selection}

Guidance informed by local suite plus live round-1 topology (1× \texttt{t3.small} vs 2× \texttt{t3.micro}); multi-instance matmul still incomplete:

\begin{itemize}
    \item Prefer validating scale-up on one larger instance before assuming multi-instance benefit
    \item Do not treat local Dask times as multi-instance EC2 matmul results
    \item Completed multi-instance \texttt{da.matmul} is evidenced in round-2 ($n{=}250$)
\end{itemize}

\section{Limitations}

\subsection{Scope Constraints}

\begin{itemize}
    \item \textbf{Matrix size range}: Local suite covers 200--2000; \textbf{no crossover} in that range; live EC2 round-1 timed out at $n{=}500$; round-2 completed at $n{=}250$
    \item \textbf{Local vs multi-instance}: Multi-node matmul wall-clock measured on EC2 at $n{=}250$ (0.2546\,s)
    \item \textbf{Dense matrices}: Sparse workloads have different communication-to-computation ratios
    \item \textbf{CPU-only}: GPU acceleration not considered; would shift cost-benefit analysis
\end{itemize}

\subsection{Generalizability}

\begin{itemize}
    \item Results are platform-specific (x86-64 CPU, OpenBLAS)
    \item Python runtime characteristics (GIL, NumPy behavior) influence outcomes
    \item Dask-specific coordination patterns; other frameworks (Ray, Spark) may differ
    \item Matrix operations workload; findings may not generalize to graph algorithms or irregular problems
\end{itemize}

\subsection{Statistical}

\begin{itemize}
    \item Confidence intervals bracket observed effects but extrapolation beyond tested ranges is speculative
    \item Three iterations per configuration (time constraint); five iterations would improve precision
    \item Single hardware platform; multi-platform validation would strengthen conclusions
\end{itemize}

\section{Future Work}

\subsection{Immediate Extensions}

\begin{enumerate}
    \item \textbf{Larger Matrices / Cloud}: Optional broader live size sweep beyond $n{=}250$; do not extrapolate local crossover
    \item \textbf{AWS Deployment}: Optional: extend live multi-instance matmul across more matrix orders
    \item \textbf{GPU Comparison}: Add cuBLAS/cuDNN implementations to explore accelerator impact
    \item \textbf{Sparse Matrices}: Test scipy.sparse operations where communication patterns differ
\end{enumerate}

\subsection{Methodological Improvements}

\begin{enumerate}
    \item \textbf{Power Analysis}: Formally determine optimal iteration count per configuration
    \item \textbf{Multi-Platform}: Test on ARM (Graviton), AMD (EPYC), and Intel (Xeon) to assess portability
    \item \textbf{Framework Comparison}: Add Ray, Spark to see if Dask overhead is framework-specific
    \item \textbf{Cost Modeling}: Integrate AWS pricing to compute cost-per-operation for each model
\end{enumerate}

\subsection{Broader Applications}

\begin{enumerate}
    \item \textbf{Machine Learning}: Apply methodology to TensorFlow/PyTorch distributed training
    \item \textbf{Scientific Computing}: Test finite element methods, molecular dynamics workloads
    \item \textbf{Data Analytics}: Evaluate DataFrame operations (Pandas vs. Dask DataFrame)
    \item \textbf{Real-Time Systems}: Measure latency distributions, not just mean completion time
\end{enumerate}

\section{Research Impact}

This work provides local-suite evidence plus live matched-vCPU EC2 rounds for a decision that cloud practitioners face routinely. Round-2 completed multi-instance \texttt{da.matmul} at $n{=}250$ (0.2546\,s). By documenting that local distributed never beats threading through 2000×2000 in committed JSON, and by recording honest round-1 timeout plus round-2 completion, this study:

\begin{itemize}
    \item Enables informed infrastructure decisions based on measurement rather than convention
    \item Provides a template for similar comparative studies on other workload types
    \item Fills the literature gap between separate threading and distributed performance studies
    \item Offers production-ready tooling that others can adapt and extend
\end{itemize}

\section{Concluding Remarks}

The choice between multi-threaded and distributed parallelism is not binary but workload-dependent. For small to medium matrix operations, threading's lower coordination overhead makes it the clear winner. Distributed execution becomes competitive only when workloads exceed single-machine capacity or when matrix dimensions reach the point where computation dominates coordination.

This project demonstrates that rigorous performance comparison requires controlling for resources, measuring multiple metrics, and testing across a range of configurations. The methodology is sound, the results are reproducible, and the tooling is extensible. Local factorial evidence is complete; live matched-vCPU EC2 multi-instance \texttt{da.matmul} is evidenced in round-2.

The research question—how do multi-threaded and distributed models compare at matched core counts—has been answered for the \textbf{local Dask proxy} (no crossover through 2000×2000) and for a \textbf{live matched-vCPU EC2} cell at $n{=}250$ (scale-up 0.001562\,s vs multi-instance 0.2546\,s on 1× \texttt{t3.small} vs 2× \texttt{t3.micro}).
