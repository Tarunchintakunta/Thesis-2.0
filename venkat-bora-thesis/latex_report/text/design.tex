\chapter{System Design}

This chapter describes the architecture of the benchmarking system, the design of each parallelism model implementation, and the measurement infrastructure.

\section{System Architecture}

The system comprises four main components:

\begin{enumerate}
    \item \textbf{Matrix Operations Module}: Implements threading, multiprocessing, and distributed matrix operations with consistent interfaces
    \item \textbf{Benchmarking Harness}: Orchestrates experiments, collects metrics, and manages result storage
    \item \textbf{Measurement Infrastructure}: Background monitors for memory and CPU sampling
    \item \textbf{Visualization Pipeline}: Generates publication-quality plots from result data
\end{enumerate}

\subsection{Design Principles}

\begin{itemize}
    \item \textbf{Separation of Concerns}: Matrix operations, measurement, and orchestration are independent modules
    \item \textbf{Reproducibility}: Fixed random seeds, versioned dependencies, deterministic execution
    \item \textbf{Testability}: All components have unit tests; pytest coverage >85\%
    \item \textbf{Extensibility}: Adding new operations or parallelism models requires minimal changes
\end{itemize}

\section{Parallelism Model Designs}

\subsection{Threading Model}

The threading implementation uses Python's \texttt{threading} module to partition matrix rows across worker threads:

\begin{verbatim}
def matrix_multiply_threaded(A, B):
    n = A.shape[0]
    C = np.zeros((n, n))
    rows_per_thread = n // self.n_threads
    
    def compute_block(start_row, end_row):
        C[start_row:end_row, :] = A[start_row:end_row, :] @ B
    
    threads = [Thread(target=compute_block, args=(start, end))
               for each partition]
    [t.start() for t in threads]
    [t.join() for t in threads]
    return C
\end{verbatim}

All threads share the \texttt{C} output array, avoiding memory duplication. NumPy's internal threading is disabled (\texttt{OMP\_NUM\_THREADS=1}) to isolate the application-level parallelism.

\subsection{Multiprocessing Model}

The multiprocessing implementation uses \texttt{ProcessPoolExecutor} for true parallel execution without GIL constraints:

\begin{verbatim}
def compute_matmul_block(A, B, start, end):
    return start, end, A[start:end, :] @ B

with ProcessPoolExecutor(n_processes) as executor:
    futures = [executor.submit(compute_matmul_block, A, B, ...)
               for each partition]
    for future in futures:
        start, end, result = future.result()
        C[start:end, :] = result
\end{verbatim}

Each process computes its partition independently and returns the result for assembly in the main process. This avoids shared memory but incurs serialization overhead.

\subsection{Distributed Model (Dask)}

The Dask implementation uses a \texttt{LocalCluster} with configurable worker count:

\begin{verbatim}
from dask.distributed import Client, LocalCluster
cluster = LocalCluster(n_workers=n, threads_per_worker=1)
client = Client(cluster)

A_dask = da.from_delayed(client.scatter(A), shape=A.shape)
B_dask = da.from_delayed(client.scatter(B), shape=B.shape)
C_dask = da.matmul(A_dask, B_dask)
C = C_dask.compute()
\end{verbatim}

Dask handles data distribution, task scheduling, and result aggregation. The \texttt{scatter} operation distributes data to workers; \texttt{compute()} triggers execution and blocks until complete.

\section{Measurement Infrastructure}

\subsection{Monitoring Design}

Memory and CPU monitors run as background daemon threads, sampling at regular intervals:

\begin{verbatim}
class MemoryMonitor:
    def __init__(self, interval=0.05):
        self.interval = interval
        self.peak_memory = 0
        self.thread = Thread(target=self._monitor, daemon=True)
    
    def _monitor(self):
        while self.monitoring:
            mem = psutil.Process().memory_info().rss / 1024**2
            self.peak_memory = max(self.peak_memory, mem)
            time.sleep(self.interval)
\end{verbatim}

The monitor thread starts before the operation and stops after, recording the maximum observed value.

\subsection{Timing Precision}

Completion time uses \texttt{time.perf\_counter()}, a high-resolution monotonic clock unaffected by system time adjustments. Typical precision is sub-microsecond on modern systems.

\section{Data Management}

\subsection{Result Storage}

Results are stored in three formats:

\begin{enumerate}
    \item \textbf{Raw Results} (JSON/CSV): Every individual run with all metrics
    \item \textbf{Summary Statistics} (JSON): Mean, std dev, confidence intervals per configuration
    \item \textbf{Visualizations} (PNG): Publication-quality plots
\end{enumerate}

This multi-format approach supports both detailed analysis and quick interpretation.

\subsection{Result Schema}

Each result record contains:

\begin{verbatim}
{
  "config_name": "Threaded-MatMul-4",
  "matrix_size": 1000,

}
\end{verbatim}

\section{Extensibility Considerations}

\subsection{Adding New Operations}

To add a new matrix operation (e.g., QR factorization):

\begin{enumerate}
    \item Implement in each parallelism model class
    \item Add to benchmark harness loop
    \item Define test cases
    \item Update visualization module
\end{enumerate}

\subsection{Adding New Parallelism Models}

To add a new framework (e.g., Ray, Spark):

\begin{enumerate}
    \item Create new class inheriting from \texttt{MatrixOperations}
    \item Implement required methods (\texttt{matrix\_multiply}, \texttt{lu\_factorization})
    \item Add to benchmark configuration
    \item Ensure cluster setup/teardown is handled in try/finally
\end{enumerate}

\subsection{Cloud Deployment}

CA2 proposes AWS EC2 with IaC provision/destroy and matched aggregate vCPUs. \textbf{Not executed} in this deliverable. Local Dask \texttt{LocalCluster} is not a substitute for that campaign. Committed CLI lacks \texttt{--scheduler-address}; remote-scheduler wiring is future work.

\section{Quality Assurance}

\subsection{Testing Strategy}

\begin{itemize}
    \item \textbf{Unit Tests}: Matrix operations correctness, measurement accuracy
    \item \textbf{Integration Tests}: End-to-end benchmark execution, result validation
    \item \textbf{Regression Tests}: Performance bounds ensure no accidental slowdowns
\end{itemize}

Total test coverage: \textbf{20} \texttt{test\_*} functions in the repository tree.

\subsection{Validation Approach}

\begin{itemize}
    \item Matrix operations validated against NumPy reference implementations
    \item LU decomposition validated via reconstruction: $A \approx LU$ within $10^{-4}$ tolerance
    \item Memory measurements validated against \texttt{/proc/[pid]/status} readings
    \item Timing validated via manual \texttt{time} command comparison
\end{itemize}

\section{Summary}

The system design prioritizes modularity, reproducibility, and extensibility. Each parallelism model implements a consistent interface, enabling fair comparison. The measurement infrastructure operates independently of the operations being measured, avoiding observer effects. The design readily extends to new operations, parallelism models, and cloud deployment scenarios.
