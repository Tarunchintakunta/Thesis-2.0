\section{Methodology}
\label{sec:Methodology}
%% ==============================

\subsection{Synthetic Workload}
A synthetic cyclical workload (\texttt{src/data/workload\_simulator.py}) of 500 timesteps combines a sinusoidal base load, periodic traffic spikes (every ~80 steps), and Gaussian noise -- generating the kind of bursty, partially-predictable demand pattern proactive scaling is meant to handle better than reactive thresholds.

\subsection{Training and Evaluation}
For each of 5 seeds (42-46), a fresh workload is generated and a fresh predictor is trained on it. All three scaling policies (Reactive HPA, Aggressive PAKS, Stability-Aware PAKS) are then run over the same workload and evaluated identically, so any difference in outcome reflects the scaling policy, not the underlying data or model.

\subsection{Metrics}
\begin{itemize}
  \item \textbf{SLA Violations}: count of timesteps where allocated pods fall below the absolute minimum required to serve the actual workload without throttling.
  \item \textbf{Over-provisioning \%}: total allocated pod-steps in excess of the minimum required, as a percentage.
  \item \textbf{Scaling Events}: count of timesteps where the pod count changes from the previous timestep -- directly comparable to NimbusGuard's own ``Total Scaling Events'' metric.
  \item \textbf{Pod Count Volatility}: standard deviation of step-to-step pod-count changes -- a finer-grained stability measure than a raw event count.
\end{itemize}

All code and results are in \texttt{paks-framework/}.
