\section{Introduction}
\label{sec:Introduction}
%% ==============================

Kubernetes' built-in Horizontal Pod Autoscaler (HPA) is reactive: it scales after a resource metric has already crossed a target, which under bursty workloads can cause SLA-violating under-provisioning during the control delay or costly over-provisioning afterward. Formal CA2 asks whether \textbf{predictive} workload forecasting combined with \textbf{adaptive} Kubernetes scaling (PAKS) improves cloud resource management under dynamic workloads versus that reactive HPA baseline.

\textbf{Research question (formal CA2):} Can predictive workload forecasting combined with adaptive Kubernetes scaling (PAKS) improve cloud resource management under dynamic workloads versus traditional reactive Kubernetes HPA?

\textbf{Objectives (formal):}
\begin{itemize}
  \item Preprocess public cloud workload data (Google Cluster Trace / Alibaba Cluster Trace) and train a workload prediction model (LSTM / TensorFlow as named in the CA2 resources table).
  \item Build an adaptive scaling engine that acts on predictions via the Kubernetes API rather than HPA-default alone.
  \item Implement and evaluate on a Kubernetes cluster hosted on AWS (EC2 compute, S3 datasets, CloudWatch metrics).
  \item Compare PAKS versus reactive HPA across varied workload intensities, reporting MAE/RMSE, utilisation, response time, throughput, scaling latency, cost, and SLA/availability.
\end{itemize}

\textbf{Honesty about the current artefact.} The binding baseline is Kubernetes HPA, not NimbusGuard. A superseded proxy framed the work as reproducing Wanigasooriya \& Ekanayake's~\cite{Wanigasooriya26} agility--stability trade-off with an MLP on synthetic cyclical loads; that code remains labelled proxy (\texttt{paks-framework/src/proxy/}) and is not the CA2 contract. This pass adds a public Google Cluster Data v1 (2010) slice, a NumPy LSTM, fail-closed 2011/2019/Alibaba loaders, a dry-run Kubernetes Scale client, and the formal metric suite. It does \textbf{not} deploy AWS or a live cluster. GCT 2011/2019 and Alibaba files are still absent (\texttt{DATA\_GAPS.md}). TensorFlow is not importable on the CPython 3.14 evaluation host and is fail-closed rather than silently replaced by MLP on the formal path.

The remainder of this report is structured as follows: Section~\ref{sec:rw} reviews reactive HPA and predictive autoscaling literature (NimbusGuard as related work); Section~\ref{sec:Design} describes HPA versus PAKS control; Section~\ref{sec:Implementation} describes the trace loader, LSTM, dry-run engine, and the quarantined proxy; Section~\ref{sec:Evaluation} reports TRACE prediction metrics on GCT v1 and SIMULATED scaling-loop metrics, with proxy tables labelled as such; Section~\ref{sec:Conclusion} states remaining blockers. The work is \textbf{not} marked complete.
