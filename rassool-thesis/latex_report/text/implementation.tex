\section{Implementation}

This section describes the implementation of the experimental artefact, including Infrastructure-as-Code (§5.1), workload generator implementation (§5.2), metrics collection (§5.3), and analysis pipeline (§5.4).

\subsection{Infrastructure-as-Code (Terraform)}

The experimental infrastructure is defined in Terraform HCL (HashiCorp Configuration Language) v1.6, organised into five modules:

\subsubsection{Tables Module (\texttt{iac/tables/})}

The \texttt{tables} module provisions six DynamoDB tables using a \texttt{for\_each} meta-argument over a map of table configurations:

\begin{verbatim}
resource "aws_dynamodb_table" "experiment_tables" {
  for_each = var.table_configs
  
  name           = each.value.name
  billing_mode   = each.value.billing_mode
  hash_key       = each.value.hash_key
  range_key      = each.value.range_key
  
  attribute {
    name = each.value.hash_key
    type = "S"
  }
  
  dynamic "attribute" {
    for_each = each.value.range_key != null ? [1] : []
    content {
      name = each.value.range_key
      type = "S"
    }
  }
  
  point_in_time_recovery {
    enabled = false
  }
  
  server_side_encryption {
    enabled = true
  }
  
  tags = merge(var.common_tags, {
    KeyDesign    = each.value.key_design
    CapacityMode = each.value.billing_mode
  })
}
\end{verbatim}

Provisioned-mode tables include auto-scaling policies defined as separate \texttt{aws\_appautoscaling\_target} and \texttt{aws\_appautoscaling\_policy} resources, following AWS best practices for target-tracking scaling.

\subsubsection{Lambda Module (\texttt{iac/lambda/})}

The \texttt{lambda} module provisions the workload generator function:

\begin{verbatim}
resource "aws_lambda_function" "workload_generator" {
  function_name = "dynamodb-workload-runner"
  role          = aws_iam_role.lambda_role.arn
  handler       = "handler.lambda_handler"
  runtime       = "python3.12"
  timeout       = 900
  memory_size   = 1024
  
  filename         = data.archive_file.lambda_package.output_path
  source_code_hash = data.archive_file.lambda_package.output_base64sha256
  
  reserved_concurrent_executions = 20
  
  environment {
    variables = {
      EXPERIMENT_CONFIG = jsonencode(var.experiment_config)
      TABLES_MAP        = jsonencode(local.tables_map)
    }
  }
}
\end{verbatim}

The Lambda package is built by \texttt{scripts/build\_lambda.sh}, which installs dependencies into a \texttt{lambda\_build/} directory and creates a zip archive. Dependencies are pinned in \texttt{requirements.txt}: \texttt{boto3==1.34.51}, \texttt{numpy==1.26.4}, \texttt{pyyaml==6.0.1}.

\subsubsection{IAM Module (\texttt{iac/iam/})}

The IAM module defines a Lambda execution role with least-privilege permissions:

\begin{verbatim}
resource "aws_iam_role_policy" "lambda_dynamodb_policy" {
  role = aws_iam_role.lambda_role.id
  
  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [
      {
        Effect = "Allow"
        Action = [
          "dynamodb:GetItem",
          "dynamodb:PutItem",
          "dynamodb:BatchGetItem",
          "dynamodb:BatchWriteItem"
        ]
        Resource = var.table_arns
      },
      {
        Effect = "Allow"
        Action = [
          "cloudwatch:PutMetricData"
        ]
        Resource = "*"
      }
    ]
  })
}
\end{verbatim}

Batch operations (\texttt{BatchGetItem}, \texttt{BatchWriteItem}) are included for the data-seeding phase but are not used in measured trials (all trials use single-item operations for consistent latency measurement).

\subsubsection{Monitoring Module (\texttt{iac/monitoring/})}

The monitoring module provisions CloudWatch log groups and metric filters:

\begin{verbatim}
resource "aws_cloudwatch_log_group" "lambda_logs" {
  name              = "/aws/lambda/dynamodb-workload-runner"
  retention_in_days = 7
}

resource "aws_cloudwatch_metric_alarm" "high_throttle_rate" {
  for_each = toset(var.table_names)
  
  alarm_name          = "${each.key}-high-throttle-rate"
  comparison_operator = "GreaterThanThreshold"
  evaluation_periods  = 2
  metric_name         = "UserErrors"
  namespace           = "AWS/DynamoDB"
  period              = 60
  statistic           = "Sum"
  threshold           = 10
  alarm_description   = "Throttle rate exceeded 10 errors/min"
  dimensions = {
    TableName = each.key
  }
}
\end{verbatim}

Alarms notify if throttling exceeds expected levels, enabling early detection of misconfiguration.

\subsection{Workload Generator Implementation}

\subsubsection{Lambda Handler (\texttt{workloads/lambda\_handler/handler.py})}

The Lambda handler receives invocation events containing trial configuration:

\begin{verbatim}
{
  "table_name": "K1-OnDemand",
  "workload": "W1",
  "duration_seconds": 300,
  "target_rate_ops_per_sec": 200,
  "zipf_s": 1.070916,
  "replication_id": 1
}
\end{verbatim}

The handler:

\begin{enumerate}
    \item Initialises the Zipfian sampler with precomputed CDF.
    \item Generates an operation schedule (GetItem/PutItem sequence with inter-arrival times).
    \item Executes operations in an open-loop (fixed inter-arrival time) using \texttt{asyncio}.
    \item Records latency (timestamp before/after each API call), consumed capacity, and throttle exceptions.
    \item Writes results to a CSV log in S3 (\texttt{s3://results-bucket/trial\_\{config\}\_\{rep\}.csv}).
    \item Emits summary metrics to CloudWatch.
\end{enumerate}

\subsubsection{Zipfian Key Generator (\texttt{workloads/generator/zipf.py})}

The Zipfian generator implements rejection-inversion sampling:

\begin{verbatim}
class ZipfGenerator:
    def __init__(self, n: int, s: float):
        self.n = n
        self.s = s
        self.hns = sum(1.0 / (i ** s) for i in range(1, n + 1))
        self.cdf = np.cumsum([1.0 / (i ** s) / self.hns 
                               for i in range(1, n + 1)])
    
    def sample(self) -> int:
        u = np.random.random()
        return np.searchsorted(self.cdf, u) + 1
\end{verbatim}

The generator is validated against \texttt{scipy.stats.zipf} using a Kolmogorov-Smirnov test (see \texttt{tests/test\_generator.py}).

\subsubsection{K3 Read Scatter-Gather (\texttt{workloads/generator/keys.py})}

For K3 (write-sharded) tables, reads require querying all 10 shard partitions:

\begin{verbatim}
async def k3_read(order_id: str, table_name: str) -> dict:
    tasks = [
        dynamodb_client.get_item_async(
            TableName=table_name,
            Key={'orderId#shard': f"{order_id}#{shard}"}
        )
        for shard in range(10)
    ]
    responses = await asyncio.gather(*tasks, return_exceptions=True)
    for resp in responses:
        if not isinstance(resp, Exception) and 'Item' in resp:
            return resp['Item']
    raise KeyError(f"Order {order_id} not found in any shard")
\end{verbatim}

This scatter-gather pattern introduces 10× read amplification, reflected in consumed RCU.

\subsection{Metrics Collection}

\subsubsection{Per-Operation Metrics (\texttt{scripts/collect\_metrics.py})}

After experiment completion, per-operation metrics are aggregated from Lambda-generated CSV logs stored in S3. The collection script:

\begin{enumerate}
    \item Downloads all CSV files for a given trial.
    \item Computes summary statistics: mean, p50, p95, p99 latency; throttle rate; throughput.
    \item Extracts consumed RCU/WCU from DynamoDB API responses.
    \item Computes cost using the cost model (§4.4).
    \item Writes aggregated results to \texttt{results/aggregate.csv}.
\end{enumerate}

\subsubsection{CloudWatch Metrics Validation}

CloudWatch metrics (\texttt{ConsumedReadCapacityUnits}, \texttt{UserErrors}) are queried using the \texttt{boto3 cloudwatch.get\_metric\_statistics} API and cross-validated against Lambda-recorded metrics. Discrepancies $>$ 5\% trigger a warning in the analysis logs.

\subsection{Analysis Pipeline}

\subsubsection{Statistical Analysis (\texttt{analysis/analyse.py})}

The analysis pipeline implements:

\begin{enumerate}
    \item \textbf{Descriptive statistics:} Mean, SD, min, max for each dependent variable by configuration.
    \item \textbf{ANOVA:} Two-way ANOVA with interaction (K × C) for each workload (W), using \texttt{statsmodels.formula.api.ols}.
    \item \textbf{Assumption checks:} Shapiro-Wilk test for normality, Levene's test for homoscedasticity. If violated, apply aligned rank transform (ART) using \texttt{ARTool} package.
    \item \textbf{Post-hoc tests:} Tukey HSD with Holm-Bonferroni correction, using \texttt{statsmodels.stats.multicomp.pairwise\_tukeyhsd}.
    \item \textbf{Visualisation:} Box plots, interaction plots, cost-performance scatter plots, generated with Matplotlib and Seaborn.
\end{enumerate}

\subsubsection{Design Checks (\texttt{analysis/design\_checks.py})}

Pre-experiment design checks validate:

\begin{enumerate}
    \item \textbf{Hot-key load:} Compute hottest-key access probability and verify it does not exceed partition limits.
    \item \textbf{Capacity plan:} Generate provisioned capacity recommendations based on anticipated load.
    \item \textbf{Cost estimate:} Predict total experiment cost (for budget approval).
\end{enumerate}

Design checks are executed via \texttt{make design} and output CSV files to \texttt{analysis/design\_checks/}.

\subsection{Testing and Validation}

\subsubsection{Unit Tests (\texttt{tests/})}

The artefact includes comprehensive unit tests (pytest):

\begin{itemize}
    \item \texttt{test\_generator.py}: Validates Zipfian distribution shape (Kolmogorov-Smirnov test, p $>$ 0.05).
    \item \texttt{test\_handler.py}: Validates Lambda handler operation generation and retry configuration (using moto to mock DynamoDB).
    \item \texttt{test\_seed.py}: Validates batch-write data seeding.
    \item \texttt{test\_stats\_cost.py}: Validates cost-model calculations against AWS pricing documentation.
    \item \texttt{test\_bib.py}: Validates bibliography entries (checks DOI URLs return HTTP 200).
    \item \texttt{test\_iac.py}: Validates Terraform syntax (\texttt{terraform fmt}, \texttt{terraform validate}).
\end{itemize}

Tests are executed via \texttt{make test} and achieve $>$ 90\% code coverage (measured with \texttt{pytest-cov}).

\subsubsection{Integration Test (Smoke Test)}

A smoke test (\texttt{make smoke}) executes a compressed experiment using moto (in-memory DynamoDB emulator):

\begin{itemize}
    \item 2 replications per cell (instead of 30)
    \item 2,000 items (instead of 1,000,000)
    \item 20-second trials (instead of 300 seconds)
    \item 10 ops/s (instead of 200/1000 ops/s)
\end{itemize}

The smoke test completes in $\sim$2 minutes and validates the end-to-end pipeline (seeding → execution → metrics collection → analysis) without AWS billing. Results are labelled \texttt{data\_source = moto} and excluded from scientific analysis.

\subsection{Deployment and Execution Workflow}

The full experimental workflow is orchestrated by a Makefile and documented in \texttt{RUNBOOK.md}:

\begin{enumerate}
    \item \textbf{Design checks:} \texttt{make design}
    \item \textbf{Terraform deployment:} \texttt{make deploy}
    \item \textbf{Data seeding:} \texttt{make seed} (batch-write 1M items, $\sim$10 minutes)
    \item \textbf{Pilot study:} \texttt{make pilot} (5 replications)
    \item \textbf{Full experiment:} \texttt{make run-matrix} (30 replications, $\sim$8 hours)
    \item \textbf{Metrics collection:} \texttt{make collect}
    \item \textbf{Analysis:} \texttt{make analyse}
    \item \textbf{Teardown:} \texttt{make teardown}
\end{enumerate}

Intermediate results are checkpointed to S3 to enable resumption after interruptions.
