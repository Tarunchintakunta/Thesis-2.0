\begin{abstract}

Serverless computing platforms employ at-least-once invocation semantics, delegating idempotency concerns to application developers. While custom serverless runtimes achieve exactly-once state mutation through asymmetric logging (e.g., Halfmoon by \citet{Qi2025Halfmoon}), managed platforms such as AWS Lambda expose only application-level primitives---conditional writes and idempotency-key patterns---to mitigate duplicate mutations during retries. Prior work has not empirically measured the duplicate-mutation reduction, latency overhead, and consumed capacity across these application-level strategies on unmodified managed infrastructure under a known retry schedule.

This research presents a controlled experimental evaluation of three write paths (P1 unconditional put, P2 conditional put, P3 idempotency-key pattern) for an AWS Lambda function writing to Amazon DynamoDB. The design injects known retry counts (1, 2, and 5 deliveries per request) by forcing timeouts after successful commits, then measures duplicate-mutation rates, end-to-end latency, and consumed DynamoDB capacity units. A live AWS pilot (50 requests per path, multiplicity 2) applies the variance-driven sizing rule from \citet{Wen2025Variance} and selects $N = 1000$ for the full campaign. The full live campaign deliveries file is empty in this submission; quantitative RQ answers for the full factorial therefore remain pending.

Functional validation on the moto testing library confirms plumbing correctness (P1 100\% duplicates at multiplicities 2 and 5; P2 and P3 0\% in-moto) but is \textbf{not} an AWS measurement of latency or capacity. Moto and the live pilot must not be treated as a completed full-campaign answer. Multi-item \texttt{TransactWriteItems} (sometimes labeled P4) is out of scope for the primary experiment and is deferred to future work.

The intended contribution is to position application-level conditional writes and idempotency-key persistence as candidate duplicate-mitigation strategies on stock managed platforms, with costs quantified only after the live campaign. Unlike runtime-replacement approaches (Halfmoon, Boki, CausalMesh, LambdaStore), these primitives require no platform modification.

\end{abstract}
