\chapter{Implementation}

This chapter describes the implementation details, build process, testing strategy, and functional validation results on moto.

\section{Development Environment and Tools}

\begin{itemize}
    \item \textbf{Language:} Python 3.12

    \item \textbf{Lambda dependencies:} boto3 1.35.36 (bundled with AWS Lambda Python 3.12 runtime; no additional dependencies packaged)
    \item \textbf{Testing:} pytest 8.x with moto 5.x for DynamoDB and Streams mocking
    \item \textbf{Linting:} ruff for code quality checks
    \item \textbf{CI/CD:} GitHub Actions workflow (not currently enabled; placeholder in \texttt{.github/workflows/})
    \item \textbf{Version control:} Git, hosted on GitHub (repository: \texttt{Tarunchintakunta/Thesis-2.0}, subdirectory: \texttt{vikas-thesis/lambda-idempotency-eval})
\end{itemize}

\section{Build Process}

The Lambda deployment package is built via \texttt{scripts/build\_lambda.sh}:

\begin{verbatim}
#!/usr/bin/env bash
set -euo pipefail

BUILD_DIR="build"
SRC_DIR="src/lambda_fn"

rm -rf "$BUILD_DIR"
mkdir -p "$BUILD_DIR"

# Copy Lambda function code
cp "$SRC_DIR"/handler.py "$SRC_DIR"/paths.py "$BUILD_DIR/"

# No external dependencies (boto3 is bundled with Lambda Python 3.12)

# Create deployment zip
cd "$BUILD_DIR" && zip -r lambda.zip . && cd -

echo "Deployment package: build/lambda.zip"
\end{verbatim}

Terraform references \texttt{build/lambda.zip} and computes a SHA256 hash to trigger redeployment only when the code changes.

\section{Testing Strategy}

\subsection{Unit Tests}

The test suite (\texttt{tests/}) contains 63 tests covering:

\begin{itemize}
    \item \texttt{test\_paths.py} (17 tests): Each write path (P1, P2, P3) under normal and error conditions (e.g., P2 conditional check failure, P3 idempotency hit).
    \item \texttt{test\_schedule.py} (8 tests): Schedule generation, deterministic seeding, factorial design coverage.
    \item \texttt{test\_driver.py} (12 tests): Invocation logic, timeout handling, capacity aggregation.
    \item \texttt{test\_streams.py} (6 tests): Stream record parsing, mutation counting, cross-validation with ground truth.
    \item \texttt{test\_metrics.py} (10 tests): Duplicate-rate calculation, latency aggregation, cold/warm separation.
    \item \texttt{test\_stats.py} (8 tests): Wilson CI, bootstrap CI, z-test, chi-square, Mann–Whitney U, Holm correction.
    \item \texttt{test\_pilot\_size.py} (4 tests): Variance estimation, power analysis, $N$ computation.
    \item \texttt{test\_analyse.py} (3 tests): End-to-end analysis pipeline (moto data).
    \item \texttt{test\_infra.py} (2 tests): Terraform validation (\texttt{terraform validate}, \texttt{terraform fmt}).
    \item \texttt{test\_budget\_estimate.py} (2 tests): Cost calculation from config/prices.yaml.
    \item \texttt{test\_check\_bib.py} (1 test): Verify all in-text citations have corresponding BibTeX entries.
    \item \texttt{test\_collect\_cloudwatch.py} (1 test): CloudWatch Logs Insights query construction.
\end{itemize}

All tests use moto to mock DynamoDB and DynamoDB Streams, avoiding the need for live AWS credentials during development and CI.

\subsection{Functional Validation}

The \texttt{make functional} target runs the complete experiment pipeline on moto with small $N$ (30 per cell for campaign, 20 per cell for sensitivity). This validates:

\begin{itemize}
    \item P1 produces 100\% duplicate mutations at multiplicity 2 and 5 (as expected).
    \item P2 and P3 produce 0\% duplicate mutations (guarded paths work).
    \item Stream-observed mutations match the function's self-reported write outcomes (0 mismatches out of 720 invocations).
    \item Analysis pipeline runs without errors, generating all tables and figures.
\end{itemize}

Functional validation results are labelled "moto functional check - NOT an AWS measurement" in all outputs.

    \item \texttt{make check-bib}: Verify BibTeX references match in-text citations.
    \item \texttt{make tf-check}: Run \texttt{terraform fmt -check} and \texttt{terraform validate}.
    \item \texttt{make budget}: Print cost estimate for pilot, campaign, and sensitivity phases.
    \item \texttt{make build}: Build Lambda deployment package (\texttt{build/lambda.zip}).
    \item \texttt{make deploy}: Run \texttt{terraform apply} to provision AWS resources.
    \item \texttt{make pilot}: Run pilot experiment (50 requests per cell, live AWS).
    \item \texttt{make pilot-size}: Compute required $N$ from pilot variance.
    \item \texttt{make campaign}: Run full campaign (N from pilot, live AWS).
    \item \texttt{make sensitivity}: Run sensitivity test (P3 crash between writes, live AWS).
    \item \texttt{make cloudwatch}: Collect CloudWatch Logs Insights data.
    \item \texttt{make analyse}: Run analysis pipeline, generate figures and summary.
    \item \texttt{make destroy}: Run \texttt{terraform destroy} to clean up AWS resources.
    \item \texttt{make functional}: Run end-to-end functional validation on moto (no AWS).
    \item \texttt{make clean}: Remove build artifacts and local run data.
\end{itemize}

\subsection{Latency and Capacity (Moto Limitations)}

Moto does not model latency or consumed capacity realistically:

\begin{itemize}
    \item \textbf{Latency:} Moto reports sub-2 ms mean latency for all paths, with no cold-start overhead. Real AWS Lambda exhibits 100--500 ms cold-start latency and 1--10 ms warm latency.
    \item \textbf{Capacity:} Moto reports fixed 0.5 WCUs for every UpdateItem, regardless of condition success/failure. Real AWS DynamoDB bills 1.0 WCU for conditional writes (whether condition passes or fails), 1.0 RCU for reads, and variable WCUs for large items.
\end{itemize}

\textbf{Conclusion:} Latency and capacity measurements from moto are \textit{not trustworthy} and must not be reported as research findings. They serve only to verify that the analysis pipeline computes metrics and CIs without errors. Live AWS campaign data is required to answer the research question.

\subsection{Sensitivity Test: P3 Crash Between Writes}

The sensitivity test simulates a scenario where the Lambda function crashes (or times out) \textit{between} writing the business item and marking the idempotency record as COMPLETED. In this case, a retry sees an incomplete idempotency record and writes the business item again---producing a duplicate mutation.

Moto results (Table~\ref{tab:moto_sensitivity}):

\begin{table}[h]

\hline
\textbf{Path} & \textbf{Mult.} & \textbf{Requests} & \textbf{Retries} & \textbf{Dups} & \textbf{Rate} & \textbf{95\% CI} \\

\textbf{Interpretation:} When the idempotency-key pattern is incomplete (crash before marking COMPLETED), P3 behaves like P1---100\% duplicate mutations. This confirms the importance of atomic idempotency-record writes (using conditional guards to prevent races). In the main campaign, P3 uses \texttt{attribute\_not\_exists} on the idempotency record to ensure atomicity, so this failure mode does not occur.

\section{Implementation Challenges and Solutions}

\subsection{Challenge 1: Injecting Timeouts Reliably}

\textbf{Problem:} Lambda may cache warm containers across invocations, and a sleep-based timeout in invocation $i$ could affect invocation $i+1$ if they run on the same container.

\textbf{Solution:} The driver uses synchronous invocation (blocking on each response) and waits for the timeout error before invoking the next delivery. Each invocation receives a fresh \texttt{delivery\_index}, so the function can distinguish first vs retry deliveries. The function only sleeps if \texttt{inject\_timeout = true} and \texttt{delivery\_index < deliveries}.

\subsection{Challenge 2: DynamoDB Streams Pagination}

\textbf{Problem:} DynamoDB Streams return records in shards, with pagination via \texttt{NextShardIterator}. Missing a page would lose mutation records.

\textbf{Solution:} The driver iterates through all shards (via \texttt{DescribeStream} $\rightarrow$ \texttt{ListShards}) and polls each shard's iterator until \texttt{NextShardIterator} is null. A sanity check compares the total number of stream records to the expected number of business-item writes.

\subsection{Challenge 3: Moto Capacity Reporting}

\textbf{Problem:} Moto reports fixed 0.5 WCUs for all writes, which is incorrect for conditional writes and idempotency-key reads.

\textbf{Solution:} Document this limitation in \texttt{STATUS.md} and the report. Do not claim moto capacity measurements as research findings. Live AWS campaign is required.

\section{Summary}

The implementation is complete, tested (63 passing unit tests), and functionally validated on moto. The artefact successfully demonstrates that P1 produces duplicate mutations, P2 and P3 prevent duplicates, and the analysis pipeline computes metrics and hypothesis tests correctly. However, moto does not provide realistic latency or capacity measurements, so live AWS campaign data is required to answer the research question quantitatively. The next chapter presents the evaluation plan and discusses how live AWS results would be integrated into the report.
